# Baratheon

Sprints, spikes and agile delivery.

> Ours is the Fury.

## The lore

Storm's End gives fury a direction. A campaign has an objective; each march has an owner and a finish. Sprinty carries the battle plan through sprints and subsprints. Spikes send scouts into uncertainty, and each return changes the plan with evidence.

## Axioms

1. **Implementation belongs to a sprint.** Use Sprinty to make goals, scope, ownership and progress explicit.
2. **Subsprints have coherent outcomes.** Break them into bounded items with dependencies and acceptance evidence.
3. **Spikes answer questions.** Bound the investigation and end with findings, a decision and a next step.
4. **Adapt visibly.** Record scope changes and use retrospectives to improve how subsequent work proceeds.

## What to do

1. **Bind the work.** Call Sprinty info, inspect the installed tool contracts and bind to the correct repository/data directory. Resume suitable work or create the sprint; identify and claim its owning item before edits.
2. **Scope the march.** Define the outcome and exclusions, then divide implementation into coherent subsprints and bounded items with dependencies and acceptance evidence.
3. **Scout uncertainty.** Use a time-bounded spike for an unresolved question. Finish with findings and a decision that updates the implementation plan.
4. **Track delivery as it happens.** Record scope changes, checks and blockers on their owning items; close work with its commit and evidence. If Sprinty is unavailable, say so and use the smallest project-approved temporary tracker, migrating it when available. Follow supported rebinding rather than filing work in another project.

## Evidence

The owning items show scope, decisions, commits and passing gates; unfinished work remains visible.
